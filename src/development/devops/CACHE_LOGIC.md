# CACHE_LOGIC.md — CoderingsTool Cache System Reference

> Reference for understanding what data is cached, where, and how.
> Last updated: 2026-03-23

---

## 1. Architecture

Two-tier caching system:

```
┌──────────────────────────────────┐
│  SQLite Metadata (cache.db)      │  ← tracks what's cached, validity status, file hashes
├──────────────────────────────────┤
│  Pickle Data Files (.pkl)        │  ← actual serialized Pydantic model data
└──────────────────────────────────┘
Location: data/cache/
```

**Key classes:**
- `CacheDatabase` — low-level SQLite operations (in `utils/cacheManager.py`)
- `CacheManager` — high-level API (save/load/invalidate/validate)

**Two storage modes:**
- **List cache** (`save_to_cache` / `load_from_cache`) — for per-response model lists (e.g., `List[PreprocessedModel]`)
- **Metadata cache** (`save_metadata_to_cache` / `load_metadata_to_cache`) — for single Pydantic models (e.g., `ExtractionMetadata`)

## 2. Cache Key Generation

Every cache entry is uniquely identified by three components:

```
(filename, step_name, variable_key)
```

### Component 1: `filename`
The SPSS source filename (e.g., `"M000000 Associatiemonitor Merk X net databestand.sav"`).

### Component 2: `step_name`
The pipeline step identifier. See §4 for the full mapping.

### Component 3: `variable_key`
Generated by `generate_enhanced_variable_key()` in `cacheManager.py`:

**Format:** `{base_key}{merge_suffix}{sample_suffix}`

| Part | Format | Examples |
|------|--------|----------|
| Base key (single var) | `{varname}` | `Q20`, `Q10`, `Qd1_combined` |
| Base key (merged vars) | `{var1+var2+...}` (sorted) | `Q1_1+Q1_10+Q1_2+Q1_3` |
| Merge suffix | `_{strategy}_{separator}_{skip}` | `_concat_semicolon_skip` |
| Sample suffix | `_{N}` or `_full` | `_2000`, `_500`, `_full` |

**Strategy codes:** `concat`, `first`, `prior`, `allcomb`
**Separator codes:** `space`, `newline`, `semicolon`, `comma`, `pipe`, `custom`
**Skip codes:** `skip` (skip empty), `noskip`

**Examples:**
- Single variable, sampled: `Q15_2000`
- Single variable, full: `Q20_full`
- Merged variables: `Q1_1+Q1_10+Q1_2+Q1_3+Q1_4+Q1_5+Q1_6+Q1_7+Q1_8+Q1_9_concat_semicolon_skip_full`
- Pre-combined variable: `Qd1_combined_2000`

## 3. Cache File Naming

**Pattern:** `{PREFIX}_{step_name}_{base_filename}_{variable_key}.pkl`

Where `base_filename` = SPSS filename without `.sav` extension.

**Example:** `004_extracted_ideas_M000000 Associatiemonitor Merk X net databestand_Qd1_combined_2000.pkl`

## 6. SQLite Schema

**Database:** `data/cache/cache.db`

**Table:** `cache_metadata`

```sql
CREATE TABLE cache_metadata (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    filename        TEXT NOT NULL,
    step_name       TEXT NOT NULL,
    variable_key    TEXT NOT NULL,
    cache_path      TEXT NOT NULL,       -- absolute path to .pkl file
    file_hash       TEXT NOT NULL,       -- MD5 hash of pickle file
    created_at      TIMESTAMP,
    last_accessed   TIMESTAMP,           -- updated on every load
    file_size       INTEGER,             -- bytes
    processing_time FLOAT,               -- seconds to compute
    status          TEXT DEFAULT 'valid', -- 'valid' or 'invalid'
    var_lab         TEXT,                 -- survey question label
    UNIQUE(filename, step_name, variable_key)
);
```

**Indexes:**
- `idx_cache_filename_step_var` on `(filename, step_name, variable_key)` — fast lookups
- `idx_cache_status` on `(status)` — for cleanup/invalidation queries

## 7. Validity Checks

`CacheManager.is_cache_valid()` performs three checks:

1. **Metadata exists:** SQLite row with `status = 'valid'` for the (filename, step_name, variable_key) tuple
2. **File exists on disk:** Verifies the .pkl file at `cache_path` still exists. Auto-invalidates if missing.
3. **Age check:** `created_at + max_cache_age_days >= now` (default: 30 days)

The MD5 `file_hash` is stored but currently used for tracking only (not automatic revalidation).

---

## 8. Invalidation

### Manual invalidation

`CacheManager.invalidate_cache()` sets `status = 'invalid'` in SQLite. Does NOT delete pickle files.

Three granularity levels:
- **Variable-specific:** `invalidate_cache(filename, step_name, variable_key)` — one entry
- **Step-level:** `invalidate_cache(filename, step_name)` — all variables for that step+file
- **File-level:** `invalidate_cache(filename)` — all steps for that file

### Cascade behavior

There is NO automatic cascade in cacheManager. Cascade is managed externally:

- **pipeline.py:** `FORCE_RECALCULATE_ALL = True` forces all steps. Otherwise each step independently checks its own cache.
- **app.py:** Per-step "Recalculate" buttons set `force_recalc=True` for that step only. The `invalidate_from_step()` function clears session state and SQLite entries from a given step onward.

### Auto-cleanup

`cleanup_old_cache()` runs on `CacheManager.__init__()` when `auto_cleanup = True`:
- Deletes pickle files + SQLite rows for entries older than `max_cache_age_days`
- Also cleans entries with `status = 'invalid'`

## 9. Save/Load Mechanics

### Saving (list mode — `save_to_cache`)

```python
# 1. Convert models to dicts
data = [model.model_dump() for model in results]

# 2. Pickle to file with fsync
with open(cache_path, 'wb') as f:
    pickle.dump(data, f, protocol=pickle.HIGHEST_PROTOCOL)
    os.fsync(f.fileno())

# 3. Calculate MD5 hash
file_hash = hashlib.md5(open(cache_path, 'rb').read()).hexdigest()

# 4. INSERT OR REPLACE into SQLite
db.save_cache_info(filename, step_name, variable_key, cache_path, file_hash, ...)
```

### Saving (metadata mode — `save_metadata_to_cache`)

Same flow but:
- Appends `_metadata` to step_name (e.g., `extracted_ideas` → `extracted_ideas_metadata`)
- Stores single model (not list)

### Loading (list mode — `load_from_cache`)

```python
# 1. Check validity (SQLite + file exists + age)
if not is_cache_valid(filename, step_name, variable_key):
    return None

# 2. Pickle load with retry (Windows file handle workaround)
data = _safe_pickle_load(cache_path)

# 3. Reconstruct Pydantic models
results = [ModelClass.model_validate(item) for item in data]

# 4. Update last_accessed timestamp
db.update_last_accessed(filename, step_name, variable_key)
```

### Robustness

- Retry logic with `gc.collect()` + 50ms sleep for Windows file handle issues
- `os.fsync()` after pickle dump for durability
- MD5 hash calculated post-write for tracking
- Automatic cleanup of partial files on error

## 10. How pipeline.py and app.py Use Cache

### pipeline.py pattern (per step)

```python
# Check cache
if not force_recalc and cache_manager.is_cache_valid(filename, step_name, variable_key):
    result = cache_manager.load_from_cache(filename, step_name, variable_key, ModelClass)
    return result

# Compute and save
result = process(...)
cache_manager.save_to_cache(result, filename, step_name, variable_key, elapsed_time, var_lab)
return result
```

### app.py pattern

- `CacheManager` stored in `st.session_state.cache_manager`
- Each step page checks cache before showing "Run" button
- "Run" button calls pipeline step with `force_recalc=True`
- `invalidate_from_step(start_step)` handles cascade:
  1. Clears `completed_steps` from start_step onward
  2. Updates `max_step_reached`
  3. Clears `pipeline_results` entries
  4. Calls `cache_manager.db.invalidate_cache()` for affected steps
- Cross-step reads: some steps load cached data from earlier steps (e.g., step 8 loads `expanded_clusters` from step 6, step 6 loads `extracted_ideas_metadata` from step 3)

## 11. Migration Considerations

When migrating dev steps 4-6 to production:

1. **CacheConfig.step_prefixes** — prefixes for dev steps (005, 006, 007) are already registered. Verify they match the final step names.
2. **Cross-step cache reads** — dev steps read from each other's cache. Ensure step_name strings match between writer and reader.
3. **Model type changes** — dev models (`models_exp.py`, `models_codeAssigner.py`) diverge from production `models.py`. Old cached data won't deserialize into new model types. Either:
   - Clear all cache after migration
   - Let old entries expire naturally (30 days)
   - Add migration logic for backwards compatibility
4. **Metadata suffix convention** — new steps must use `_metadata` suffix for single-model cache entries (e.g., `taxonomy_metadata`, `mece_codes_metadata`).
5. **Production step names to retire** — `embeddings`, `code_assignment`, `codebook_generation_reasoning`, `expanded_clusters`, `codebook_refinement`, `codebook_refinement_enriched`, `code_assignment_direct` will become unused.
